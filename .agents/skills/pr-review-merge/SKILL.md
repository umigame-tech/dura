# PR のレビューからマージまで

## いつ始めるか

このスキルは作業の**最後**に行う仕上げの手順であり、作業の最初に行うものではない。

- 実装の依頼や、タスクを探して進めるスキルと一緒に指定された場合は、まずそちらに従ってタスクを決め、実装し、コミット・プッシュして PR を作成する。このスキルの手順 1 は、その PR ができてから始める。
- 現在のブランチにまだ PR がない、または実装が終わっていない場合は、レビューを始めない。既存の別の PR を探してレビューすることもしない。
- 指定されたのがこのスキルだけで、現在のブランチの PR が既にある場合は、そのまま手順 1 から始める。

## 前提

- GitHub CLI（`gh`）が使え、認証済みであること。
- 対象は現在のブランチの PR とする（`gh pr view --json number,url,baseRefName,headRefName` で確認する）。

## 手順

### 1. レビューする

PR の差分（`gh pr diff`、または `git diff <base>...HEAD`）を読み、指摘を洗い出す。

- 可能であれば、これまでの作業の文脈を持たない別のエージェントやサブエージェントにレビューさせる。使えない場合は自分で行い、実装時の意図に引きずられずに差分そのものから判断する。
- 見る観点は、正しさ（ロジックの誤り、境界条件、エラー処理の漏れ）、セキュリティ、既存の挙動を壊していないか、テストの不足、明らかな重複や不要なコードとする。
- 書式や好みの問題は指摘しない。
- リポジトリにレビューや開発の規約（CLAUDE.md、AGENTS.md、CONTRIBUTING.md など）があれば従う。

各指摘を次のどれかに分類する。

- **要修正**：バグ、セキュリティ上の問題、既存機能の破壊、PR の目的を満たしていない点。
- **任意**：改善案だが、直さなくても問題がないもの。
- **要判断**：直し方が複数あって仕様や設計の選択が必要なもの、依頼内容と矛盾するもの。

### 2. 次に進む先を決める

- 要判断が 1 件でもあれば、修正もマージもせずに止めて報告する。
- 要修正が 0 件なら手順 4 へ進む。
- 要修正があれば手順 3 へ進む。

### 3. 修正する

要修正の指摘だけを直し、任意の指摘には手を付けない。

- 修正後、プロジェクトのテスト・型チェック・リントを実行し、通ることを確かめる。
- コミットしてプッシュし、手順 1 に戻る。2 回目以降は、前回からの変更分と、前回の指摘が直っているかを重点的に見る。
- レビューと修正の繰り返しは最大 3 回とする。3 回目でも要修正が残る場合は止めて報告する。

### 4. CI を待つ

`gh pr checks --watch` で完了を待つ。

- 失敗したら原因を調べ、修正してプッシュし、手順 1 に戻る。この修正も手順 3 の回数に含める。
- 失敗の原因がこの PR の変更と無関係（不安定なテスト、インフラ障害など）と判断できる場合は、再実行を 1 回だけ試す。それでも失敗すれば止めて報告する。

### 5. マージする

すべてのチェックが通り、要修正の指摘が残っていなければマージする。

- マージ方式はリポジトリで許可されている方式に従う。指定がなければ squash とする（`gh pr merge --squash`）。
- コンフリクトが機械的に解決できる場合は解消してプッシュし、手順 1 に戻る。解決に判断が要る場合は止めて報告する。
- ブランチ保護で人の承認が必要な場合は、マージを試みずに止めて報告する。

## 止めて報告する場合

次のどれかにあたるときは、それ以上進めずにユーザーに報告する。

- 要判断の指摘がある。
- 繰り返しの上限に達した。
- CI の失敗を解消できない。
- 人の承認が必要、または解決に判断を要するコンフリクトがある。
- 履歴の書き換え（force push）やブランチ・データの削除など、取り消しにくい操作が必要になる。

報告には、PR の URL、残っている指摘とその分類、止めた理由、ユーザーに決めてほしいことを含める。

## 完了時の報告

マージしたら、PR の URL、レビューと修正を繰り返した回数、直した指摘の要約、見送った任意の指摘を簡潔に報告する。
